# 重命名规则

> **一句话**：改的是「这张图发出去那一行文字」——规则一行一条，页面按黑白名单页的形态做（逐条列表 + 新建行 + 清空行），导入一律就地合并，解析只有 `RenameRules` 一份。

## 1. 规则改的是什么

相册里的文件名是手机给的（`IMG_20261110_153102`、`Screenshot_2026...`），发进聊天就变成一串没法读的字。
重命名规则把**发出去的文字**换掉：左边写原文件名（去扩展名），右边写要发的文字。

| 规则 | 原文件名 | 微信里看到的 |
| --- | --- | --- |
| `003033 -> 征和工业` | `003033.png` | `征和工业`（第二次起 `征和工业 +2`） |
| `截图 -> 微信截图` | `Screenshot_20261110` | `微信截图` |

三条边界，改规则前必须知道：

- 只改**发出去的文字**，手机本地文件名不动；
- 只认文件名，不认内容 —— 同一张图改个名字就是另一条规则；
- 计数键跟着**新名字**走（`RepeatCounter` 记的是最终文字），所以改规则等于给这张图开一份新计数；
- 规则不命中就发原名，不会变成空（想不发文字用「文字过滤」的黑名单，见 [IMG-LABEL-TEXT-FILTER.md](IMG-LABEL-TEXT-FILTER.md)）。

## 2. 规则格式（解析正本 `RenameRules.parse`）

`feature/imglabel/RenameRules.java` 是唯一解析器：微信进程侧用它、设置页也用它（新建校验、列表展示、导入），
**页面上不另写一套 split**——两份解析迟早对不上，用户会在页面里看到「格式正确」的规则被发送端丢掉。

| 分隔符 | 示例 | 备注 |
| --- | --- | --- |
| `->` | `003033 -> 征和工业` | 首选写法，新建规则永远写成这一种 |
| `=>` | `003033 => 征和工业` | 手写导入时容错 |
| `=` | `003033 = 征和工业` | 同上 |
| 制表符 | `003033\t征和工业` | 从表格里粘过来的常见形态 |

其余约定：

- 一行一条；`#` 开头整行是注释，空行忽略；
- 分隔符取**第一个命中**的（先找 `->`，没有再找 `=>`、`=`、TAB），且要求左边不是空串；
- 两边 `trim()` 后都必须非空，否则这一行丢掉；
- 解析结果保序（`LinkedHashMap`），页面上列表的顺序就是文件里的顺序；
- 同一个原名写两次，后一条覆盖前一条（Map 语义）—— 新建规则时直接拦掉，不让用户制造这种歧义。

## 3. 页面形态（与黑白名单页同一套）

改版前是一整块 260dp 的文本框 + 保存/导入/导出/复制/粘贴五行：表里有几条、哪条写错了、正要改哪条，全得靠人读文本。
现在按 `docs/UI.md` §3 的三节结构：

| 节 | 内容 |
| --- | --- |
| **规则** | 逐条成行：标题是原名，摘要是新名，行尾 40dp ✕ 删这一条（`AppIcons.Close` 细描边、中性色，见 [UI.md](UI.md) §4 图标表）；表空时显示「还没有规则」占位行，说清「不配置就按原文件名发送」 |
| **新建与清空** | 一张卡：`新建规则`（行尾 `AppIcons.PlusThin`）走贴底输入弹层；已有一条以上时才出现 `清空规则`，走贴底二次确认 |
| **导入与导出** | 一张卡：从文件导入 / 从剪贴板导入 / 导出到文件 / 复制到剪贴板 |

排版硬规则：卡内**不画分隔线**，分层靠拆卡 + 卡间 `Spacer(12.dp)`（[UI.md](UI.md) §7 第 9 条）；
两张卡之间漏了 Spacer 就会糊成一整块（改版首版就是这样，实机发现后补的）。

所有写操作都是**即改即存**，页面上没有保存按钮：新增 / 删除 / 清空 / 导入落地即写 `img_label_rename_rules`，
反馈统一走 Toast。这一点和「发送记录」的编辑动作同源 —— 有显式保存按钮的页面，用户忘了点就白改。

## 4. 新建规则的校验（四种情况都挡在弹层里）

| 输入 | 提示键 | 为什么挡 |
| --- | --- | --- |
| 空串 | `rename_new_rule_empty` | 空规则没有意义 |
| 含换行 | `rename_new_rule_single` | 一次只加一条；批量走「导入」。输入框是单行的，手打打不出换行，这道分支实际拦的是**粘贴多行** |
| `RenameRules.parse` 解不出左边 | `rename_new_rule_format` | 提示里给出 `原名 -> 新名` 的写法 |
| 左边与已有规则重名 | `rename_new_rule_exists` | 否则写进去是后覆盖前，用户以为加了两条 |

校验回调返回 `null` 表示通过、返回字符串表示错误文案，弹层自己显示、不关闭（`TextInputDialogSpec.validate`）；用户一改输入，红字自动撤掉。

真机验收记录（MuMu 安卓 12，2026-11-10）：空串 → 「规则不能为空」、`nofmt` → 「格式不对，写成「原名 -> 新名」」、`RENAMED_OK=X` → 「这条原名已经有规则了」，三次弹层都没关；点取消后列表仍是原来那一条。

## 5. 导入是「合并」，不是「替换」

`mergeRows(raw): Pair<Int, Int>` 返回 `(追加条数, 跳过条数)`：

- 解析导入内容 → 逐条比对已有规则的**原名**；
- 已存在 → 跳过（**不覆盖**：用户的现有配置优先）；
- 新原名 → 按规范写成 `原名 -> 新名` 追加到表尾；
- 回显按「新增 N 条、跳过 M 条」/「新增 N 条」/「没有可导入的规则」三选一。

为什么不整体替换：导入这个动作的心理预期是「加点新的」，而整体替换会一次抹掉攒了很久的表。
真要从头来，用「清空规则」再导入 —— 那是两个明确动作，不会误伤。

## 6. 生效时机

| 环节 | 位置 |
| --- | --- |
| 配置键 | `ConfigKeys.IMG_LABEL_RENAME_RULES`（String，整表一个字符串，一行一条就是文件的全部内容 —— 比多行 StringSet 好导入导出） |
| 解析 | 微信进程侧每批一次，`RenameRules.parse` 结果为空或抛异常就发原名 |
| 应用 | `RenameRules.apply(rules, label)`，命中返新名 |
| 与过滤的先后 | **先套重命名、再判文字过滤** —— 过滤看的是「最终会发出去的那行字」，加 ` +N` 之前 |

所以：改规则不影响已经发出去的图；改规则后同一张图的下一次发送算新名字的第一条（计数从 1 起）。
