# 文案与命名规范

> **一句话**：开关本身就是「启用」—— 用户拨动开关这个动作已经表达了「打开 / 增强」，文案里不要再写一遍；名字只回答一个问题：这个功能是什么。

适用范围：`values/strings.xml` / `values-en/strings.xml` 里所有**用户可见**的文案 ——
分区名（`category_*`）、功能名（`feature_*_switch`）、说明（`feature_*_summary`），
以及二级菜单的标题与条目（`img_label_*`、`item_*`）。

本文是文案命名的**单一正本**。`ui/FeatureCatalog.kt` 与两份 `strings.xml` 的注释都指向本文。

---

## 1. 四条硬规则

### 规则一：名称里不写「启用」「增强」

开关 / 卡片本身就是「启用」的载体，`启用 XXX` 里的「启用」是纯冗余；
整个模块就是「增强」，分区名 / 功能名再挂一个「增强」是同义反复。

| ❌ 别写 | ✅ 写成 |
| --- | --- |
| 启用发送图片文件名 | 发送图片文件名 |
| 启用重复图片计数 | 重复图片追加次数 |
| 发送增强 | 发送 |
| 相册增强 | 相册 |

同理不写：「开启」「打开」「支持」等开关本身已蕴含的动词，以及「增加 XXX **功能**」
里的「功能」二字。

### 规则二：名称里不写多余符号

用户可见文案**不用引号**（`「」`、`『』`、`《》`）、不用句末省略号、不用装饰性符号。
界面元素名直接书写；需要点明控件类型时用**半角空格**分隔（见规则三）。

> 这条只管**用户看得见的文案**。代码注释、`docs/` 文档、日志里的 `「」` 不受此限 ——
> 那里靠引号区分「界面上的名字」和叙述文字，是有用的。

### 规则三：新增 / 隐藏的元素写「动词 + 内容 + 控件类型」

如果一个功能是在原界面上**新加**或**去掉**一个原本存在的东西（按钮 / 菜单项 / 入口 / 弹窗 / 项），
名称写成三段式，中间用**半角空格**隔开：

```text
增加 + 内容 + 控件类型        （原本没有、是我加的）
隐藏 + 内容 + 控件类型        （原本就有、被我拿走）
```

| ❌ 别写 | ✅ 写成 |
| --- | --- |
| 启用图片长按菜单 | 增加 复制文件名 菜单项 |
| 隐藏发送按钮 | 隐藏 发送 按钮 |

- **控件类型**用词：`按钮` / `菜单项` / `入口` / `弹窗` / `开关` / `项`。
- **内容**只写界面上的那个名字，不加页面前缀 —— 页面由**分区名**交代，重复写就是冗余。
- 对象本身就是个双字词、没有可拆的「内容」时，两段式即可（`隐藏横幅`）。

### 规则四：副标题说清「塞到了哪」，其余能省就省

副标题的核心职责是**告知位置** —— 标题只说「加了 / 隐藏了什么」，用户还想知道
「塞到了哪个地方」（在相册、在聊天页、在右上角更多里 …）。**位置说不清的功能必须补副标题**；
主标题连同分区名已经把话说全时，不写（`switchSummaryRes = null`，卡片上只剩标题一行）。

判断顺序：先问「用户开着开关去哪里找它」，答不清 → 补位置；答得清 → 省略。

| ❌ 别写 | ✅ 写成 |
| --- | --- |
| `增加 文件名 文字`（没有副标题）—— 不知道文字补在了哪 | `增加 文件名 文字` + 「相册批量发送时，每张图后面」 |
| `发送图片文件名` + 「相册选图发送后，按选图顺序在每张图后补一条文件名」 | `发送图片文件名`（**没有副标题**：分区「发送」+ 标题已说全） |
| `重复图片追加次数` + 「同一张图第二次发会变成 +2、第三次 +3……」 | `重复图片追加次数`（**没有副标题**：二级页里的开关，标题已说全） |

## 2. 先判类型：这个功能是「增强」还是「新增」？

**关掉开关，看微信上少了什么：**

| 关掉开关后…… | 类型 | 名称写法 |
| --- | --- | --- |
| 原来**就有**的东西变了（行为 / 顺序 / 内容） | **增强** | 直接写「东西」本身：`发送图片文件名` |
| 原来**没有**的东西没了（多出来的按钮 / 菜单项 / 入口） | **新增** | `增加 + 内容 + 控件类型`：`增加 复制文件名 菜单项` |

一句话记：**「本来就有、被我改了」→ 名词；「本来没有、是我加的」→ 增加 XX XX。**

## 3. 两层文案，各写什么

`FeatureSpec` 里一条功能有两个文案字段，职责不同：

| 字段 | 谁看得见 | 写什么 |
| --- | --- | --- |
| `switchTitleRes` | **卡片上的功能名**，用户唯一可见 | 按本规范起名（短、无「启用 / 增强」、无符号） |
| `switchSummaryRes` | 卡片下方那一行说明，**可空** | 只在主标题装不下时才写，见下 |

界面上只渲染这两个字段（见 `ui/FeatureTab.kt` 的 `FeatureEntry`）。

### 副标题（`switchSummaryRes`）

**位置优先。** 先问「用户开了开关，去哪里找这个功能」—— 答不清就补副标题，
答得清（分区名 + 标题已说全）就不写。`switchSummaryRes` 是 `Int?`，
不写就传 `null`，卡片上那一行直接不存在（不是留空行）。

四条限制，写之前逐条过：

1. **位置优先**：说清功能塞到了哪里（相册 / 聊天页 / 输入框 / 长按菜单 …），
   这是副标题存在的第一理由；标题已经说清位置的功能不写副标题。
2. **不写机制与后果**：它怎么实现的（Hook 哪个方法、走哪条通道）、别的控件因此怎么了，一律不写。
3. **一行说完**：中文 ≤ 20 字、英文 ≤ 60 字符，**能不用逗号就不用**。
4. **不写「A 自动 B」句式**：主语不是功能本身的句子，读起来像在解释别人的反应。

> 判断标准：把副标题遮住，只读主标题，**用户还知不知道打开会发生什么**。
> 知道 → 删掉副标题；不知道 → 副标题就只写「不知道的那一点」。

### 同一条规则管到别处

| 位置 | 字段 / 资源 | 判据 |
| --- | --- | --- |
| 功能卡片下方展开的二级入口 | `detailEntrySummaryRes` | 入口名已经说清进去做什么 → 不写。**不列**里面有哪些项目 |
| 设置页条目 | `item_*_summary` | **状态类**（主题=当前值、玻璃光效=完整/简约）必须留；**说明类**若只是标题的展开写法就删 |
| 二级菜单里的开关 | `item_*_summary_on/off` | 同上，状态描述留，标题的复述删 |
| 任何用户可见界面 | 类名 / 控件 ID / Hook 点 / API 版本等开发者向字段 | **不进界面** —— 用户看不懂；完整档案留在 `docs/` |

例外只有一条：**破坏性操作**（如「重置模块」）保留一行说明**范围**，因为「重置」这个词本身不交代会重置掉什么。

## 4. 分区名（`category_*`）

分区名是**名词**，只交代「这一组功能作用在哪个页面 / 哪个层面」，不带「增强」：

| 资源 | 文案 |
| --- | --- |
| `category_img_label` | 发送 |

目前只有一个分区。**只有当一个功能不属于任何一个已有分区时才新开分区**，
并且要同时更新 `ui/FeatureCatalog.kt` 顶部注释、本表与两份 `strings.xml`。

| --- | --- | --- | --- | --- |

## 6. 新增功能时的落地清单

1. 先按 §2 判类型，再按 §1 的四条规则写出 `switchTitle`。
2. 落到 `values/strings.xml` **与** `values-en/strings.xml`（中英同步，一条都不能少）。
3. 英文按同一套逻辑：`Enable xxx` → `xxx`；新增类 → `Add "xxx" button` / `Add "xxx" entry`
   （英文里引号是标注界面标签的排版惯例，**保留**；规则二只管中文文案）。
4. **副标题先留空**（`switchSummaryRes` 不传），过一遍 §1 规则四：主标题真的装不下才补，补就补一行。
5. 只有**新开分区**时才动 `category_*`，并同步 `ui/FeatureCatalog.kt` 顶部注释与本文件 §4。
6. 回头看一眼 §5 的对照表，确认新名字和现有名字**读起来是一套的**。

## 7. 反例速查

| 别写 | 因为 |
| --- | --- |
| 启用 XXX | 开关已经说了「启用」 |
| XXX 增强 / 增强 XXX | 整个模块就是增强，分区 / 功能名不必再声明 |
| 增加 XXX 功能 | 「功能」二字冗余，直接说增加了什么 |
| 「XXX」按钮 | 用户可见文案不用引号 |
| 增加复制文件名菜单项 | 三段式要用半角空格分隔：`增加 复制文件名 菜单项` |
| 副标题「走接管通道逐张重放发送入口」 | 讲的是实现机制，不是这个功能是什么（规则四） |
| 副标题「同名图片第二次发会变成 +2、第三次 +3」 | 主标题的展开写法（规则四） |
